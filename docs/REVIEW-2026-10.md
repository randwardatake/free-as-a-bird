## 2. Fixes applied

All of these are in the working tree, with regression tests. Nothing has
been committed: the repository has no commits yet.

### Y1. Sync requests trusted the peer's declared frame length

- **Was:** `readFrame` allocated the length a peer announced (up to 8 MB)
  before reading, and sync requests used the 8 MB response limit. About 37
  streams were enough to kill a node under `MemoryMax=300M`. No membership
  was needed.
- **Now:** `internal/node/wire.go` grows the buffer as bytes arrive
  (`io.CopyN` into a `bytes.Buffer`). Requests are capped at
  `maxRequestFrame` (64 KiB). `readJSON` takes the limit as a parameter.
- **Verified (Measured):** 20 truncated "8 MB" frames allocated 160 MB with
  the old code and under 1 MB now (`TestReadFrameDoesNotTrustDeclaredLength`).

### Y2. Relayed-only members stalled blob downloads for 60 s

- **Correction:** the first report said NAT'd members could not sync
  through a hub at all. That was wrong. A hub is a full member, NAT'd
  members connect to it directly, and it stores and forwards posts.
- **Real problem (Source + PoC):** a stream over a relayed (limited)
  connection waits for hole punching (`swarm.go`, `waitForDirectConn`): up
  to 30 s per sync request and 60 s per blob download. The three fetch
  workers jammed whenever a relayed-only member was a candidate.
- **Now:**
  - `direct()` and `dataPeers()` in `internal/node/discovery.go`. Sync,
    blob fetching and the maintenance loop only use peers we reach directly.
  - Hub relays keep libp2p's small default limits on purpose. They only
    carry the hole-punching handshake, so heavy users cannot drain a shared
    hub. (The first report suggested `WithInfiniteLimits`; that was
    withdrawn because it conflicts with the bounded-public-node goal.)
  - Hubs now set `libp2p.ForceReachabilityPublic()`. libp2p starts the relay
    service only on public reachability, so a hub used to relay nothing
    until AutoNAT confirmed it.
  - README and ARCHITECTURE.md updated.
- **Verified (PoC):** `TestRelayedMemberDoesNotStallFetch` builds a real
  relay on loopback: 60 s before, 0.03 s after, stable across runs.
